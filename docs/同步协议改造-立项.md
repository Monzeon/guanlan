# 同步协议改造 · 立项（audit-2026-11-11 的 U1 / U2）

> 状态：立项，未开工。上一轮刻意没动，理由成立；这一份把「为什么必须一起改、怎么改、怎么验收」写实。

## 一、现状：两个现象，一个根因

**U1 — 快照与指纹期间独占整库锁。** 链路是这样的：

```
手机 GET /api/peer/info
  └─ host_refresh()
       ├─ fingerprint()      ← with self.lock（排他），把整库按 rowid 序列化重算 sha256，
       │                        再把 uploads / body / notes 里每个文件逐字节读一遍
       └─ build_snapshot()   ← 同样 with self.lock，sqlite backup + zlib 压缩 23MB 库与附件
```

`self.lock` 就是 `server.LIBRARY_LOCK`（`server.py:608`），而每个请求拿库连接时都要先拿共享锁（`server.py:627`）。
于是快照期间所有普通读写请求都在排队。上一轮实测这一个窗口 **16.34 秒**，库 23.3MB —— 库越大、附件越多，窗口越长，且没有上限。

根因不是「锁用错了」，而是**用整库快照当作同步的最小单位**：为了拿到「某一瞬间的完整库」，只能把库冻住。

**U2 — 拉取窗口内的写入被静默抹掉。** 客户端 `sync_once` 先算本地指纹、比对远端，判定要拉，然后：

```
_pull() → 下载 download.zip → apply_snapshot() → os.replace(staged_db, db_path)
```

`apply_snapshot` 是整库文件替换。从「算指纹」到「替换完成」这段时间里（含下载、解压、校验），用户在本机写的任何东西，替换后就不存在了 —— 因为新库是远端某一时刻的镜像，本地这几笔写入既没进快照，也没有墓碑，也没有事后补偿。没有任何提示。

`host_submit` 有同一问题：上传期间电脑端自己的写入，被上传的包整体覆盖。

根因同上：**协议以「整库覆盖」表达变更，而不是以「变更」表达变更。** 没有墓碑，删除也就无法传播 —— A 删掉一条，B 拉取后本地没了，但 B 下一次 push 会把它带回来（B 的快照里没有「已删除」这个信息）。

两个问题同根，分开修会互相拆台：只解 U1（不持锁做快照）会把 U2 的窗口从「毫秒级替换」拉长到「秒级构建」，丢数据更容易；只解 U2（拉取改为合并）则必须有自己的变更序列，而那正是 U1 想要的增量信息。所以一起立项。

## 二、目标（都可验收）

1. 发起同步时，普通接口不再排队：快照构建期间持续写入，写请求 P95 < 50ms、P99 < 200ms。
2. 拉取不再吞掉本地写入：拉取窗口内写入的条目，结束后仍在库里；不一致的地方落冲突副本，不静默丢。
3. 跨设备删除能传播：A 删、B 拉、B 再推，条目不会复活。
4. 快照仍是整库一致镜像（能独立还原），不是逐表拼凑的半成品。
5. 43 条现有回归全绿；v1 快照至少还能被应用一个大版本。

## 三、设计

### 3.1 变更序列（oplog + 墓碑）

```sql
CREATE TABLE sync_oplog (
    seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- 单库单调，等价于「变更版本号」
    tbl        TEXT NOT NULL,
    row_pk     TEXT NOT NULL,                      -- 主键的规范化字符串
    op         TEXT NOT NULL CHECK (op IN ('ins','upd','del')),
    payload    TEXT NOT NULL DEFAULT '{}',         -- 非删除时的新行内容（列名→值）
    device_id  TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE TABLE sync_tombstones (
    tbl        TEXT NOT NULL,
    row_pk     TEXT NOT NULL,
    deleted_seq INTEGER NOT NULL,
    deleted_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (tbl, row_pk)
);
```

- 用 `AFTER INSERT/UPDATE/DELETE` 触发器写，和现有 FTS 触发器并列，不改业务代码。
- 只覆盖需要同步的业务表：`claims`、`sources`、`predictions`、`decisions`、`clips`、`clip_notes`、`clip_annotations`、`boards`、`reading_*`、`bible_*`。`code_counters` 不进 oplog（它是本地计数器，靠 `next_code` 的 `MAX` 兜底重排）。
- 删除时写墓碑，`DELETE` 触发器里同时写 op='del' 与墓碑行；墓碑保留 90 天或按 rev 截断，两者取先到。

### 3.2 快照不再持锁

三件事拆开做：

1. **一致性读取交给 sqlite**：`sqlite3.Connection.backup()` 在 WAL 下复制的是某个读事务的一致视图，写者不被阻塞（这一点必须在阶段 1 实测确认，不能只信文档）。当前 `build_snapshot` 用的是同一个 API，问题只在它外面套了排他锁。
2. **指纹从快照里算，不再单独扫生产库**：现在 `fingerprint()` 扫一遍全库 + 全附件，`build_snapshot()` 再扫一遍，等于同一份数据读两次。改成：backup 出一份 → 对这份副本算指纹 → 副本进 zip。指纹与快照必然同源，也省掉一次全库读。
3. **附件用「清单 + 增量哈希」**：维护 `data/.sync-media-cache.json`，键为 `相对路径`，值为 `(size, mtime_ns, sha256)`；只对 size/mtime 变了的文件重算哈希。复制前后各取一次目录清单，若集合不一致（并发增删）就重来一次，仍不一致则记 `partial` 并让下次同步追平。
4. 排他锁只包住「`current_zip` 指针交换 + host meta 落盘」这一瞬间（毫秒级），不再包住构建。

### 3.3 拉取改为「应用变更集」

- `/api/peer/info` 返回 `head_rev`（当前最新 seq）与 `snapshot_id`。
- 新增 `/api/peer/changes?since=<rev>`：返回 `since` 之后的 oplog 增量包（zip 内 `changes.jsonl` + 本批涉及的新附件）。
- 客户端 apply：
  ```
  BEGIN IMMEDIATE
    逐条按 seq 应用（ins → INSERT OR REPLACE，upd → 按 pk 更新，del → 删除并落本地墓碑）
    记 applied_rev = 本批最大 seq
  COMMIT
  ```
- 本地 `seq > applied_rev` 的行天然保留，下一次 push 时随增量发给对端。
- 冲突（同一 pk 两端都改过）：保留本地行，把远端版本写进 `conflicts/` 下的行级副本，界面上给一条「N 条冲突待处理」。不再整库存 zip。
- 兜底：`since` 太旧（超出 oplog 保留窗口）或校验失败 → 退回 v1 整库快照，但**先**把本地状态存成冲突包，**再**替换，最后把冲突包里的行按 pk 补回（补不进的仍然留副本）。

### 3.4 兼容与迁移

- `manifest.json` 的 `format` 升到 `guanlan-library-v2`，多带 `head_rev`；v1 包仍可 apply（整库替换路径，标记 `legacy=true` 进日志）。
- 首次升级做一次全量回填：`INSERT INTO sync_oplog (...) SELECT ... FROM 各业务表`，一次性把现有数据变成 seq 1..N，并记 `applied_rev = N`。
- 开关 `GL_SYNC_V2=0` 一键退回旧路径，出问题当天可退。

## 四、分阶段（每阶段独立可回滚）

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | 指纹与快照合并成一次副本读取；附件哈希缓存；排他锁缩到指针交换 | 快照期间 20 次/秒写入全在 50ms 内返回；快照 sha256 与「停服后 sqlite backup 的 sha256」一致 |
| 2 | oplog + 墓碑触发器，只写不读（先观察完整性） | 任意操作序列后，用 oplog 重放能还原出与现库等价的库（逐表逐行比对） |
| 3 | `/api/peer/changes` + 客户端 apply 变更集（局域网 peer 先上，云同步后上） | 拉取窗口内每 100ms 写一条，事后全部在场；applied_rev 单调 |
| 4 | 删除传播 + 行级冲突副本 + 界面上的冲突计数 | A 删 B 拉 B 推，条目不复活；冲突包可按行查看/采用/丢弃 |

阶段 1 与 2 互不依赖，可并行；3 依赖 2；4 依赖 3。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| oplog 体积与触发器开销 | 只记业务表；`seq` 按窗口截断（保留 90 天或最近 5000 条）；每季度 `VACUUM` 一次 |
| backup 与 checkpoint 打架、WAL 膨胀 | 构建期间临时调高 `wal_autocheckpoint`；构建完跑一次 `wal_checkpoint(PASSIVE)`；监控 `-wal` 文件大小 |
| 附件并发增删导致快照半新半旧 | 前后两次清单比对 + 重试一次 + `partial` 标记 |
| 云同步是 `peer_sync` 的子类，改动要两处同步 | 协议层放在 `peer_sync` 的公共方法里，`cloud_sync` 只换传输；验收用例两套都跑 |
| Android 端 sqlite 版本 | 阶段 1 先在 Android 上跑 `PRAGMA`+backup 的最小验证；3.7+ 才进 v2 |

## 八、顺带定口径（U3 / U5）

**U3｜PDF 抽取截断**
现在按 200 页 / 6 万字符静默截断，仍返回 `stored`，用户以为整本解析完了。建议改成：

```json
{"stored": true, "partial": true, "pages_stored": 200, "pages_total": 486,
 "note": "正文过长，仅解析前 200 页"}
```

前端在阅读页顶部给一条常驻提示条，可点「解析更多」。不报错 —— 截断是止损，不是失败；但必须可见。

**U5｜云同步后台线程**
设置页开关打开后 `start_cloud_sync_background()` 没被调用，等于开关是装饰。建议：开关变化时立即启停线程，语义定为「写完即推 + 间隔兜底」双轨（`interval` 不是唯一触发）。否则应把设置页文案改成「仅在本机写入时推送」，别留一个不生效的开关。

## 九、明确不做

- 不改任何界面交互与路由。

- 不动 `bible_*` / `reading_*` 的表结构（只给它们挂 oplog 触发器）。
- 不做多主（multi-master）冲突自动合并 —— 冲突给人看，这是产品判断，不是技术能力问题。
